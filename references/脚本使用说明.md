# Skill中的辅助脚本：路径与执行方式

本Skill的 references/ 保存五份V3核心、案例资料规范、本说明与初稿交付规则；scripts/ 保存三个Python脚本。五核心与原《V3五文件执行包》逐字节一致，V3研究规则及首次留出结果保持原样。辅助工具版本为1.0.0；本次补充资料规范，不新增一轮文献学习版本。

入口分工：首次输入、追加或迁移新案例资料时，先读[案例资料规范](案例资料规范.md)，填写材料输入说明，并在第0步保存资料考察记录。使用脚本时读取本说明，再按[新案例执行入口](新案例执行入口.md)执行研究。只使用文档时，由Agent按五核心与资料规范手工执行。脚本需要Python 3.10或更高版本，只使用标准库；三个脚本保持在Skill根目录的同一 `scripts/` 目录；五核心位于 `references/`。Agent选择当前环境中可用的Python解释器，`python` 是下列示例的解释器名称。

| 文件 | 触发条件 | 完成条件 |
| --- | --- | --- |
| [init_case.py](../scripts/init_case.py) | 新案例还没有成果目录；或恢复时缺少骨架文件 | 创建缺少的文件，保留已有内容；研究阶段仍未完成 |
| [index_materials.py](../scripts/index_materials.py) | 首次登记材料；材料新增、变化、删除或迁移 | 本次可读文件完成哈希登记；旧编号、版本与人工元数据保留 |
| [check_case.py](../scripts/check_case.py) | 结构化证据表填写后；阶段交付前；换Agent或换电脑后 | 错误项为零；警告逐项登记实际回读或未核查范围 |

## 1. 一次启动

定位本Skill根目录。按资料规范分开材料、成果和受限归档，指定本次拟交付的材料目录；它不是整个案例总目录。初始化按脚本位置自动查找五核心；指定独立成果目录。Windows PowerShell示例：

```powershell
$casePack = 'D:\技能目录\case-paper-drafter'
$caseMaterials = 'D:\案例写作\青川案例\材料'
$caseOutput = 'D:\案例写作\青川案例\成果'

python "$casePack\scripts\init_case.py" --case-dir "$caseOutput" --name '青川案例'
python "$casePack\scripts\index_materials.py" --case-dir "$caseOutput" --materials-dir "$caseMaterials"
python "$casePack\scripts\check_case.py" --case-dir "$caseOutput" --write-report
```

上述路径只是占位示例，填写实际位置。脚本不依赖原文献项目、1131份参考PDF、API密钥或互联网。其他系统使用对应路径与Python解释器。

默认第2步创建边界与状态表，不假定案例一定按阶段组织。已经确定过程任务时，在首次初始化命令增加 `--organization process`。省略 `--core-dir` 时，脚本先使用Skill中包含全部五核心的 `references/`；该处不完整时，再检查独立执行包根目录。两处均不完整时，报告检查位置并提示恢复文件或指定目录，不创建成果骨架。此查找不依赖终端当前目录。

核心文档另存其他目录时，增加 `--core-dir '实际五核心目录'`。显式指定优先于自动查找；相对路径仍相对终端当前目录解析。该目录缺少任何核心文件时直接列出缺少的文件，不转用其他目录。重复初始化仍核对已有配置中的核心哈希，不改写旧配置或分析成果。

初始化只创建骨架。Agent继续执行第0—3步；已有问题时保留已有决定。文件中的 `CASE_TOOLS_PLACEHOLDER` 及“尚未完成”提示，只有在对应内容完成后才移除。

## 2. 材料编号与版本

`材料登记.json` 是登记的权威文件；`材料登记.csv` 是供查看的派生表。编辑JSON中的 `metadata` 补充形成主体、材料类型、材料形成日期、事件时期、原语和译本版本。再次登记保留这些字段。编辑CSV不会自动写回JSON。

脚本递归登记普通文件，不提取PDF正文、不执行OCR、不转写录音。它跳过符号链接、指向材料目录外的目录、`.git`、`__pycache__`、`.DS_Store` 与 `Thumbs.db`；跳过位置写入JSON。成果目录位于材料目录内时，也会排除整个成果目录。材料目录与成果目录不能是同一个目录。

编号形式为 `S0001`、`S0002`。登记按以下规则保留身份：

- 同一路径内容变化：保留编号，材料版本加1，保存旧哈希。历史哈希不能恢复旧文件正文；旧版本仍用于研究时，另保存旧文件并单独登记。
- 只有一个旧路径消失，且只有一个新路径拥有相同哈希：按相同字节迁移路径，保留编号与版本。这不证明来源主体相同。
- 同字节存在多个候选：不猜测重命名关系；新路径分配新编号。
- 材料删除：标记 `missing`，保留编号，后续不重复分配旧编号。
- 同字节多个文件：列出重复组；不据此判断转载关系、作者身份或来源独立性。

`filesystem_modified_at_utc` 只是操作系统的文件修改时间，不能当作材料形成日期或事件发生日期。材料内容的身份和日期仍由Agent从真实来源核查。

材料新增或内容变化后，运行：

```powershell
python "$casePack\scripts\index_materials.py" --case-dir "$caseOutput"
```

材料目录迁移后，核对身份再明确登记：

```powershell
python "$casePack\scripts\index_materials.py" --case-dir "$caseOutput" --materials-dir '新材料目录' --relocate
```

普通登记不改写事实表、解释矩阵、提纲或草稿。材料路径被新文件替换时，脚本按该路径的新版本登记；Agent负责判断来源身份是否也改变。

## 3. Agent如何填写结构化证据

按五核心写 `01-材料与事实表.md` 与 `06-证据与解释矩阵.md`。启用脚本核查时，将引用的证据另登记在 `事实与证据.csv`。CSV是用于编号与版本核查的辅助表，不替代完整的材料分析。它最初只有表头，没有虚构事实。

| 列 | 填写内容 |
| --- | --- |
| `evidence_id` | 案例内唯一证据编号，例如 `E0001` |
| `source_id` | 一份已登记材料编号；一行绑定一个来源 |
| `source_version` | 本次实际回读的登记版本，来自JSON |
| `source_sha256` | 本次实际回读版本的文件哈希，来自JSON |
| `locator` | 原材料定位，例如 `L12-L15`、`PDF第4页`、`00:03:15` |
| `statement` | 实际材料直接支持的事实、原话或限定陈述 |
| `material_status` | `目标`、`设计`、`观察`、`陈述`、`规范`、`协商参数`、`条件预测`、`建议`、`待确认`之一 |
| `analysis_status` | `支持`、`待检验`、`材料不足`之一；“支持”是Agent的登记判断 |

CSV使用标准逗号分隔。包含逗号、双引号或换行的字段用CSV规范转义。可以使用Python的 `csv.DictWriter` 或Excel填写，保持列名和顺序。一个主张使用多个来源时，分别登记证据编号，在正文引用这些编号。

`L12-L15` 指UTF-8文本的物理行，包括空行。脚本能核查TXT、MD、CSV、JSON、JSONL的行号范围。PDF页、Word段落、工作表单元格、音频时间戳及非UTF-8文件由Agent回读；报告保留未自动核查警告。

材料版本改变时，旧证据会报告版本不一致。Agent回读后决定更新证据绑定、保留旧版本来源或撤回主张。脚本不会自动升级证据，也不因哈希相同就证明陈述成立。

## 4. 阶段交付与核查结果

`阶段登记.json` 中第0—9步使用四个状态：`not_started`、`in_progress`、`complete`、`blocked`。初始化全部为 `not_started`。只有按五核心完成该阶段的动作与完成条件，才把对应状态写成 `complete`，并在 `执行记录.md` 保存决定、事实/矩阵版本和缺口。

日常检查：

```powershell
python "$casePack\scripts\check_case.py" --case-dir "$caseOutput" --write-report
```

第0—3步交付前：

```powershell
python "$casePack\scripts\check_case.py" --case-dir "$caseOutput" --stage 3 --write-report
```

`--stage 3` 要求0、1、2、3全部登记完成。第4—7步交付用 `--stage 7`；完整草稿复核用 `--stage 9`。未指定 `--stage` 时，只检查当前结构、绑定和已经声明完成的阶段；空骨架不会自动算完成。`--stage` 不是宣布完成阶段的命令。

脚本检查五核心及材料哈希、未登记的新文件、来源/证据编号、证据版本、CSV必填字段、状态枚举、阶段文件、占位符、正文编号及有限本地链接。第1步必须绑定来源与证据；第6—9步必须引用证据编号。它不会分析数字口径、判断事实真实性、读取理论全文、确认因果机制或评价投稿质量。

| 退出码 | 含义 | Agent下一步 |
| --- | --- | --- |
| `0` | 本次结构检查无错误；仍可能有警告 | 阅读警告，再执行人工核查；不把它称为研究质量通过 |
| `1` | 核查发现错误 | 按报告修订登记、定位或阶段成果，再核查 |
| `2` | 参数、文件读取或登记格式错误 | 修正具体运行条件；本次没有有效的核查结论 |

报告明确标记 `semantic_verification: not_performed`。`--write-report` 只更新 `脚本核查报告.json`，不改写人工的 `09-复核记录.md`。登记脚本逐文件原子写入生成的登记文件；若CSV输出失败，JSON可能已经更新，以JSON为准并在恢复写入条件后重新登记。

## 5. 换电脑或换Agent

交接五核心、案例资料规范、三个脚本、本说明、本次可交付材料、现有阶段成果、三个JSON登记文件、CSV证据表和 `执行记录.md`。身份映射与受限原件继续按资料规范另存。保持相对目录关系时可以直接恢复。材料另存位置时按第2节登记迁移。

五核心位置改变但内容相同时，在核查命令增加 `--core-dir '新的五核心目录'`。核查不会默默改写配置中的旧位置；Agent在 `案例配置.json` 和执行记录中保存当前定位，保留原文件哈希。

核心哈希不同时，先比较实际文档与既定决定，登记模板版本迁移，再更新绑定。重复初始化不会覆盖既有配置或接受不同核心哈希。过程与状态表组织方式改变时，更新配置的 `organization`（`process` / `state`），保存相应第2步文件并记录理由。

## 6. 直接交给Agent的指令

```text
请调用 $case-paper-drafter，并读取当前阶段所需的资料规范与同版本核心。
完整包位置：【实际位置】
自有材料位置：【实际位置】
独立成果目录：【实际位置】
已有问题、决定或草稿：【实际内容；没有则写未确定】
先盘点实际可读资料，核对问卷/访谈/录音及派生文件关系。
按资料规范登记形成者、执行者、事件时期、形成日期与已核查范围。
把资料考察和具体缺口保存到00-任务范围.md，不要求所有资料类型齐全。
先确认当前成果；新案例用init_case.py创建骨架，已有文件保留。
用index_materials.py登记当前材料。事实和解释仍由你回读材料后填写。
按《新案例执行入口》执行当前阶段，维护结构化证据表和执行记录。
阶段动作完成后登记complete，再用check_case.py核查对应阶段。
核查错误逐项修正；警告写明实际核查或未核查范围。
脚本通过只代表所列结构检查，研究结论以真实证据和理论核查为准。
```

附件环境不能运行Python时，按五核心手工执行并交付阶段成果。三个脚本是可选辅助工具，五核心仍是研究与写作规则的权威来源。
